# Directory Plugin Feature Inventory (CTF Rewrite)

## Scope and Boundary

- Rewrite target: `ctf/`
- Plugin slug: `directory`
- Directory is a deterministic profile-and-discovery plugin with unified user/admin UI surface and role-gated server controls.
- Legacy `platform/` is reference-only; not modified.

## Intent and Outcome

Directory in CTF provides authenticated users with a deterministic profile-and-discovery experience, unified admin workflows on the same UI surface, server-enforced policy controls (claimed/unclaimed guardrails, privacy filters, anti-scraping), and parity-safe delivery across web and Android.

**Scope boundary — Directory lists, it does not transact.** Directory exists only to list members and the skills they hold (drawn from the shared skills taxonomy) and to let people read a member's profile. Directory does **not** include messaging/chat or session booking. Those belong to the **Foundation** plugin. Any "Direct Chat", "Message", "Book Session", or appointment-availability affordance that appeared on the Directory surface came from the retired Replit design mockups, not from this spec, and has been removed (see Change Log, 2026-06-16). When a member wants to reach a provider or book time, that flow lives in Foundation.

**Directory lists skills; it does not "share" or "offer" them.** Directory only shows the skills a member holds so others can find and read them. It is **not** where a member offers or shares those skills for exchange — that is **Foundation** (Foundation is where members list the skills they share). This distinction matters because Directory also carries **unclaimed, community-generated profiles** — people who were nominated but have no account yet — so a Directory listing is not the person offering anything. Describe Directory as "members and the skills they hold", never as members "sharing" or "offering" skills.

## Target User Features

1. **Browse and read profiles.** Directory is a list of members and their skills. Open Directory to see their profiles; each profile shows a member's job title, sector, and skills. Any signed-in member can browse and read every active, listed profile — **even if they do not have a profile of their own**. Some profiles are made by members themselves; others are community-generated (a member nominated someone who has no account yet) and carry a "Community generated" badge. Directory only *lists* these skills so others can find and read members — it is not where members offer or share their skills for exchange (that is Foundation).
2. **Create, update, or delete your own profile.** A member can add their own directory profile (name, an optional headline, a short bio, location, and skills from the shared taxonomy), then edit or remove it later. Having your own profile is not required to browse others.
3. **Search and filter the list.** The search box matches a member's name, headline, bio, skills, and location (city/state/country); sector filter chips narrow the list to one sector.
4. **Directory is no longer public-facing** (2026-05-18). The `isPublic` toggle was removed; every authenticated member sees every active, non-deleted profile. There is no anonymous projection route. Legacy public URLs are not redirected — backwards compatibility is intentionally not preserved.
5. Announcement consumption in user-visible contexts.
6. Deterministic validation limits for description, selectors, and URL fields.
7. **"Weavers of the Commons" contributor badge on the profile detail** (2026-07-18, web +
   mobile-responsive; 2026-07-19, android — #1680). A claimed profile whose member holds the Contributor Access badge
   (`eligible = TRUE AND revoked_for_cause = FALSE`) shows the braid badge next to the name; the
   read routes set `hasWeaversBadge` on claimed profiles only (guarded cross-plugin read —
   `lib/contributor-access/badge.ts`). Positive-only: members without it show nothing (no empty
   slot, no absence state) and community-generated (unclaimed) profiles never carry the field.
   Clicking the badge opens a small dialog (honest copy, no verification/vetting claim) with a
   "How it's earned" link to the signed-in explainer page
   `/apps/directory/weavers-of-the-commons`. Owned by the Contributor Access module — see
   `ctf-contributor-access-feature-inventory.md` for the full badge spec.

## Target Admin Features

1. Admin controls exist in **two** coexisting places (owner decision, 2026-06-06): (a) the **inline, admin-only "Attach to account" control** on the Directory profile detail, and (b) a **dedicated Directory admin page** at `/admin/directory` (web) and a Directory Admin screen on Android. Both attach an unclaimed profile to a user account (assign); the dedicated page additionally lists every profile and supports edit and unclaimed-only delete.
2. Admin profile list, create, update, assign, and unclaimed-only delete flows.
3. Admin announcement list/create/update/deactivate flows.
4. Admin skills compatibility and selector governance operations.
5. Claimed/unclaimed guardrails enforced as hard server-side policy constraints.

This reverses the earlier 2026-06-03 "inline-only, deliberately no standalone admin page" rule. The dedicated admin page lives at `/admin/directory` (web, gated by the same `evaluatePluginAccess` + `isAdmin` check the directory admin API uses) and as the "Directory Admin" screen in the Android app. The inline "Attach to account" control on the profile detail is unchanged.

## API Surface and Route Map

Implemented routes:

- User/authenticated:
  - `GET /api/directory/profile`
  - `POST /api/directory/profile`
  - `PUT /api/directory/profile` — full upsert of the caller's own profile. Bound on web by the member-facing "Edit my profile" form (`components/directory/directory-profile-edit.tsx`), opened from the owner's own profile in the detail view. The form loads `GET /api/directory/profile`, prefills every editable field, and re-sends the complete field set on save (a missing field is reset to null/'' by `toProfileInput`, so the form never omits one). The Specializations picker has a typed-search box that filters the full (still scrollable) taxonomy list in place, plus a "Your skill not listed? Add it" box that accepts free-text labels (`proposedSkills`) for skills not in the taxonomy — those persist to `directory_profile_proposed_skills` and round-trip back into the form. `GET /api/directory/profile` returns both `proposedSkills` (the member's own free-text additions, editable) and the merged display set `pendingSkills`.
  - `DELETE /api/directory/profile`
  - `GET /api/directory/list` — also decorates each **claimed** item with the
    `hasWeaversBadge` boolean (guarded read of `contributor_access_eligibility` via
    `lib/contributor-access/badge.ts`; unclaimed items never carry the field; empty result on any
    error so the list can never fail because of it).
  - `GET /api/directory/profiles/:id` — fetch one active directory profile by id, behind the same `requireDirectoryReadAccess` gate as the list. Backs the auth-gated deep-link page `/apps/directory/profile/[id]` (the destination a shared `ShareLink` points at): a signed-in member opens the Directory with that profile's detail; an unauthenticated visitor is redirected to the directory landing by the page, never reaching this route. Returns `{ member }` (a `DirectoryProfile`) on 200, `{ ok: false, code: DIRECTORY_NOT_FOUND }` 404 when no active profile matches, or `DIRECTORY_PERSISTENCE_UNAVAILABLE` 503. A **claimed** member also carries the `hasWeaversBadge` boolean (same guarded contributor-access read as the list; never set on an unclaimed profile).
  - `GET /api/directory/skills`
  - `GET /api/directory/sectors`
  - `GET /api/directory/job-titles`
  - `GET /api/directory/announcements`
- Public: none. The `GET /api/directory/public` and `GET /api/directory/public/:id` routes
  (v2 anonymous projection) were removed 2026-05-25 — they leaked full profile data
  (including payment addresses) to unauthenticated callers, contradicting the
  no-public-facing decision above. `/apps/directory/[handle]` now redirects to the
  authenticated Directory shell.
- Admin:
  - `GET /api/directory/admin/profiles`
  - `POST /api/directory/admin/profiles`
  - `PUT /api/directory/admin/profiles/:id`
  - `PUT /api/directory/admin/profiles/:id/assign`
  - `DELETE /api/directory/admin/profiles/:id`
  - `POST /api/directory/admin/profiles/:id/takedown` — remove a community-generated (unclaimed) profile **at the person's request** and suppress its Quora URL. Body `{ reason }` (required). Deletes the profile and its skill rows, inserts the normalized Quora URL into `directory_suppressed_quora_urls`, and writes a `directory.admin.profile.takedown` audit event. Denies (409) a claimed, non-community-generated, or URL-less profile; use the ordinary delete for those. **Distinct from delete** (which is for duplicates/accidents and does not block re-adding).
  - `GET /api/directory/admin/suppressed-urls` — admin read of the Quora-URL suppression list (active blocks first, newest first) for the admin takedown screen.
  - `POST /api/directory/admin/suppressed-urls/:id` — lift a suppression (override) so the URL can be listed again. Body `{ reason }` (required). Sets `is_overridden = true` and writes a `directory.admin.takedown.override` audit event; denies (409) an already-lifted entry.
  - `GET /api/directory/admin/skills` — admin-only selector-compatibility read (gated by `requireDirectoryAdminAccess`). Returns the full shared taxonomy — `sectors`, `jobTitles`, `skills` (via `listTaxonomySectors`/`listTaxonomyJobTitles`/`listTaxonomySkills`) — plus a `selectorCompatibility` summary with the count of each. Backs the admin "skills compatibility and selector governance" feature; read-only, never mutates the taxonomy.
  - `GET /api/directory/admin/announcements`
  - `POST /api/directory/admin/announcements`
  - `PUT /api/directory/admin/announcements/:id`
  - `DELETE /api/directory/admin/announcements/:id`

Admin surfaces (rendered pages, not API routes):

- Web: `/admin/directory` (`app/admin/directory/page.tsx` → `DirectoryAdminShell`). Server-gated with `evaluatePluginAccess({ requireUsername: false })`; non-admins are redirected to `/apps/directory`. The shell binds to the admin profile routes above: `GET /api/directory/admin/profiles` (list), `PUT /api/directory/admin/profiles/:id` (edit), `PUT /api/directory/admin/profiles/:id/assign` (attach), `DELETE /api/directory/admin/profiles/:id` (unclaimed-only delete). ## Data Model and Storage Contracts

1. `directory_profiles` — Directory profile records with claimed/unclaimed state.
2. `directory_announcements` — Directory announcements with activation/deactivation state.
3. Skills hierarchy (shared taxonomy) — Selector-backed taxonomy data.
4. Profile policy contracts — Claimed/unclaimed state and assignment constraints.
5. Public projection contracts — Privacy-filtered output shape for unauthenticated callers.

### Name fields on `directory_profiles`

A directory profile stores the person's name in two columns, `first_name TEXT` and `last_name TEXT`
(both nullable), and renders them as "First Last". `first_name` is required on input;
`last_name` is optional. This applies to both claimed and unclaimed profiles. There is no
`display_name` column on `directory_profiles` — it was removed in the v3 cleanup (see the Change Log
entry dated 2026-06-02 and the `post/0001_directory_display_name_to_first_last.sql` migration).

### New columns on `directory_profiles` (SkillsHunt + Clerk username co-change, 2026-05-11)

1. `source TEXT NOT NULL DEFAULT 'admin' CHECK (source IN ('admin', 'self', 'community-generated'))` — drives the "Community generated profile" badge in the UI.
2. `invited_by_username TEXT NULL` — denormalized from `skills_hunt_directory_profiles.invited_by_username` so the (auth-gated) profile page renders attribution without a join.
3. `unclaimed_handle TEXT NULL` — auto-generated vanity handle for unclaimed profiles. Format: `community-<6char-hex>` (no leading `@` in storage; `@` is presentation only). Cleared/ignored once `claimed_by_user_id` is set. Uniqueness is enforced by a case-insensitive partial unique index (`directory_profiles_unclaimed_handle_key` on `lower(unclaimed_handle)` WHERE `unclaimed_handle IS NOT NULL`), not an inline column constraint — so `Community-7F3A2B` and `community-7f3a2b` cannot coexist, and the migration block can drop/recreate the index without tripping over a constraint-backed index on the fresh-schema path.
4. `deleted_at TIMESTAMPTZ NULL` — soft-delete for GDPR and moderation removals; `is_active` remains in place but `deleted_at` takes precedence for visibility filters.

### Location columns on `directory_profiles` (surfaced 2026-07-11)

`city`, `state`, `country` (each `TEXT`, nullable at the column level; `varchar(100)` on the carried-over v2 rows) hold the member's location. Values are the plain names from the shared location standard (`packages/web/lib/geo/locations.ts`): `country` e.g. "United States", `state` a US-state name (when country is the United States) or a free-text region otherwise, `city` free text. Location matters especially for non-US members — Directory feeds nearly every other plugin, so the country in particular must be accurate.

**`country` is REQUIRED on input (2026-07-16); `city` and `state` stay optional.** Enforced end to end at the app layer: the member self-edit form and the admin edit drawer gate their Save on a non-empty country (with a "(required)" label), and `validateProfileInput` (`lib/directory/repository.ts`) rejects any create/update whose country is blank — so all three write routes (`PUT /api/directory/profile`, `POST`/`PUT /api/directory/admin/profiles`) refuse a blank country. SkillsHunt-generated profiles already carry a country (SkillsHunt requires it at submit time). The columns stay physically nullable because the account-deletion anonymization path deactivates the row (`is_active = false`) and nulls city/state/country, and because a small number of legacy/imported rows predate the requirement. A matching DB CHECK (`is_active = false OR country present`) is intended but **deliberately deferred** until those legacy blank-country rows are backfilled — adding it before then would make claiming a legacy blank-country profile, or accepting a pre-requirement SkillsHunt submission with a null country, fail as a raw constraint violation; see the `schema.sql` note by `directory_profiles_source_check` and the 2026-07-16 Change Log entry.

**These are the SAME column names v2 used** (`directory_profiles.city/state/country` in the prod snapshot `ctf/schema-prod4.6.2026.sql`). The v2→v3 clone carried the rows forward with those columns and their values intact, but v3's `schema.sql` never declared them and the app never read them — so the data looked missing. Declaring them in `schema.sql` (`ADD COLUMN IF NOT EXISTS`, a no-op on the clone that preserves the values in place) plus reading/writing them in the repository, routes, and UI is the whole "port" — **no data-copy migration is needed** (unlike skills/bio/profile_url, whose v3 targets differ from v2 and are backfilled in `post/0005`–`0007`; the legacy `users` table has no location columns). Edited on web through the member self-edit form and the admin edit drawer using the shared `CountrySelect`/`StateField` controls; cleared on service-scoped deletion. Length is capped at 100 (`DIRECTORY_MAX_LOCATION_LENGTH`) to fit the carried-over `varchar(100)` type. **Android:** location is displayed on the mobile profile detail; editing it on mobile is deferred (needs the searchable mobile country picker, cf. #1380) and mobile admin saves preserve the stored value untouched.

### Backfill (one-shot, idempotent)

For every `directory_profiles` row where `claimed_by_user_id IS NULL AND unclaimed_handle IS NULL`, assign `unclaimed_handle = 'community-' || encode(gen_random_bytes(3), 'hex')`. Retry on case-insensitive unique-index collision. Establishes consistent `@handle` URLs on day one.

### Skills backfill from the legacy array (one-shot, idempotent)

Per-profile skills are stored in the normalized `directory_profile_skills` junction (`profile_id` → `skill_id` → `skills_taxonomy_skills`); the profile view reads skills only from that join. The original platform instead stored skills as a free-text array column on the profile itself (`directory_profiles.skills TEXT[]`, up to three names). The v2→v3 clone carried the profile rows and that legacy array column forward, but nothing populated the junction, so every cloned profile showed zero skills. `post/0005_directory_backfill_skills_from_legacy_array.sql` copies each legacy skill name into the junction by matching it case-insensitively against `skills_taxonomy_skills`. It is guarded (no-ops on a fresh DB with no legacy `skills` column), idempotent (`ON CONFLICT (profile_id, skill_id) DO NOTHING`), and deterministic (`DISTINCT ON` picks one taxonomy skill per name when a name is ambiguous). Names with no taxonomy match are skipped.

### Pending (not-yet-promoted) nominated skills on a profile

A community-generated profile created from a SkillsHunt nomination can carry free-text skills that are not yet in the taxonomy. Those nominated skills only exist as a proposal in `skills_hunt_proposed_skill_promotions` (one row per distinct free-text skill, `status` starting at `proposed`), not in `directory_profile_skills` — so before the skill is promoted, the profile's Specializations section had nothing to show and rendered "No skills listed yet."

The profile links back to its originating submission through `skills_hunt_directory_profiles` (`directory_profile_id` → `submission_id`), and a proposal row references that same submission via `source_submission_id`. `loadProfilePendingSkills` in `ctf/packages/web/lib/directory/repository.ts` follows that chain to read the still-pending proposals (`status <> 'promoted'`) for the profile and returns them as `DirectoryProfile.pendingSkills`. The profile detail (`directory-profile-detail.tsx`, Specializations section) renders them as muted, dashed-border "· pending review" chips alongside the real accent taxonomy chips, so the section is never empty when a skill was nominated. Once a pending skill is promoted (added to the taxonomy and the proposal marked `promoted`) and a profile references it through `directory_profile_skills`, it renders as a normal taxonomy skill and drops out of the pending set. Read-only join; no schema or contract change.

### Member-added free-text skills on a member's own profile (`directory_profile_proposed_skills`)

The self-edit form lets a member add a skill that is **not** in the taxonomy through a "Your skill not listed? Add it" box (for example "Game design", which the taxonomy does not currently include). These free-text labels persist to `directory_profile_proposed_skills` — columns `id`, `profile_id` (UUID, keyed to the profile), `skill_label TEXT`, `status TEXT DEFAULT 'pending'`, `created_at`, `updated_at`; a unique index on `(profile_id, lower(skill_label))` blocks duplicates per profile, and a `profile_id` index supports the per-profile read. The label is capped at `DIRECTORY_MAX_PROPOSED_SKILL_LENGTH` (40) and the count at `DIRECTORY_MAX_PROPOSED_SKILLS` (10), enforced both in the form and defensively in `normalizeProposedSkills`/`validateProfileInput`.

`upsertOwnProfile` replaces the set on every save (`replaceProfileProposedSkills`). `mapProfileRow` reads them via `loadProfileProposedSkills` (status `pending`) and exposes two fields: `proposedSkills` (the member's own additions, returned to the edit form so they can be changed or removed) and `pendingSkills` (the de-duplicated display set = SkillsHunt nominations **plus** these self-added labels, minus any that already match a selected taxonomy skill name). The profile detail and the mobile list already render `pendingSkills` as muted "· pending review" chips, so a self-added skill shows there with no display-layer change. The table is `profile_id`-keyed and is cleared with the profile in `deleteOwnDirectoryProfile`.

**Routing to the central promotion queue.** Self-added labels are not a Directory-local promotion: they feed the one cross-app intake every skill addition goes through. The scheduled job `proposeSkillPromotions.mjs` (workflow `skills-proposal-issues.yml`, every 6h) scans `directory_profile_proposed_skills` (status `pending`) alongside accepted SkillsHunt nominations, skips any label already in the taxonomy or already tracked, and files one `skill-proposal` GitHub issue per new label into `skills_hunt_proposed_skill_promotions` (with `source = 'directory'`). That GitHub issue **is** the review queue — there is deliberately no in-app promotion screen. When the owner approves — an `addSkill` change merged and applied via the owner-run `seed-skills-taxonomy.yml` workflow (`ctf/scripts/lib/applyTaxonomyChange.mjs`) — the apply step (a) **auto-attaches** the now-official taxonomy skill to every profile that proposed that label — an idempotent `INSERT … ON CONFLICT DO NOTHING` into `directory_profile_skills`, scoped to the occupation the skill was promoted under — and (b) flips the matching `directory_profile_proposed_skills` row to `promoted`. So the member's muted "pending review" chip becomes the real accent taxonomy chip in place, with nothing to re-select. The attach is one-shot (only `pending` rows attach), so a member who had already removed the proposal is not re-given the skill.

### Description backfill from the legacy column (one-shot, idempotent)

The original platform stored the profile blurb in a legacy `directory_profiles.description` column (`VARCHAR(140) NOT NULL`); v3 renders the blurb from `bio`, which was never populated for cloned profiles — so a carried-over profile showed only a name. `post/0006_directory_backfill_bio_from_legacy_description.sql` copies `description` → `bio`, but only where `bio` is empty, so an in-app edit is never overwritten. Guarded (no-ops without the legacy column) and idempotent.

The legacy contact columns (`directory_profiles.signal_url`, `directory_profiles.quora_url`) are deliberately left in place and **not** copied into the core `users` table: that table is the cloned legacy table keyed by a legacy uuid and is disconnected from v3's Clerk identity (`directory_profiles.claimed_by_user_id` holds the Clerk id directly). The contact URLs stay on the profile row (tied to the claiming member via `claimed_by_user_id`) and will be surfaced by the Foundation/SocketRelay contact flow when that is built. Quora for verification is handled separately by the Unlock plugin (`unlock_verification_submissions.quora_profile_url`).

### Plugin extension, audit, and deletion tables

Beyond the profile and skills tables above, Directory owns five supporting tables:

- `directory_user_extension` — the rule-114 plugin extension keyed by `user_id` (PK). Holds `profile_visibility` (default `workspace`; the directory is no longer public-facing, so it is hard-set to `workspace`), the service-scoped deletion marker `service_deleted_at`, the member's payment addresses (`venmo_address`, `monero_address`, `bitcoin_address`, `service_credits_address`), and `updated_at`. Written on every self-upsert and on service-scoped deletion. On service-scoped deletion the row is tombstoned (kept so `service_deleted_at` records the marker and rejoin can recreate clean defaults) and every contact/payment address column is set to `NULL`, satisfying the deletion contract's "clear discoverability/contact data" requirement.
- `directory_profile_change_events` — append-only change/audit log. Columns: `id`, `actor_id`, `command` (e.g. `directory.profile.upsert`, `directory.admin.profile.create`), `policy_status` (`allow`/`deny`), `reason`, `target_type`, `target_id`, `metadata` (jsonb), `created_at`. One row per profile mutation; retained for accountability (not removed on service-scoped deletion).
- `directory_deletion_events` — deletion accountability trail. Columns: `id`, `user_id`, `scope` (e.g. `service`), `plugin_id`, `requested_at`, `processed_at`, `result` (e.g. `completed`), `created_at`. One row per deletion request; retained for compliance.
- `directory_profile_tags` — a `(profile_id, tag_id)` junction carried over from v2. Currently vestigial: nothing writes it (no tag UI or route exists); it is only cleared, by `profile_id`, when a profile is deleted. Kept for schema continuity; removal is tracked as cleanup.
- `directory_suppressed_quora_urls` — the "remove at the person's request" takedown suppression list. Columns: `id`, `normalized_url` (the Quora URL in SkillsHunt's canonical form), `original_url`, `reason`, `removed_profile_id` (the deleted profile's id, for the record), `created_by_user_id`, `created_at`, `is_overridden` (bool), `overridden_by_user_id`, `overridden_at`, `override_reason`. A row with `is_overridden = false` is an **active block**: that Quora URL cannot be listed in the directory again — auto-generated from a SkillsHunt accept (`maybeAutoGenerateDirectoryProfile` skips and logs `directory.profile.generate`/`deny`), or added by an admin/member (`createAdminProfile`/`upsertOwnProfile` throw `directory_quora_url_suppressed` → HTTP 409) — until an admin lifts the block (override). A partial unique index (`WHERE is_overridden = false`) keeps at most one active block per URL; a URL may be re-suppressed after an override. This is **distinct from the ordinary `directory.admin.profile.delete`** (for duplicates/accidents, no block). Takedown and override are audited in `directory_profile_change_events` (`directory.admin.profile.takedown`, `directory.admin.takedown.override`).

## Security, Privacy, and Compliance Controls

1. Server-side authorization is enforced on every admin endpoint.
2. Admin controls are hidden in the frontend but authorization is always server-enforced (presentation-only hiding is not authorization).
3. Claimed/unclaimed mutation guardrails are enforced server-side.
4. Public projection returns privacy-minimized fields only.
5. Public endpoints enforce anti-scraping controls and rate-limited access.
6. CSRF protection is required on every write endpoint, including the member self-service `POST`/`PUT`/`DELETE /api/directory/profile` routes (origin + `x-ctf-csrf` header, via `ensureMutationCsrf`).
7. Audit logging is required for admin mutations (allow and deny outcomes) and for the read commands the audit contract defines. Every audit-contract command now emits `logDirectoryAudit` on success and failure: `directory.profile.upsert`, `directory.profile.delete.service`, `directory.list.fetch`, `directory.admin.profile.create`, `directory.admin.profile.assign`, `directory.admin.profile.delete` (including the `not_found` deny), and `directory.admin.announcement.upsert` (create / update / deactivate).
